# K–2 mystery challenge

Frame a concrete mission with a success condition, a playable 3–7 step sequence, and two or more constraints. Preserve every object, variant, or comparison the parent names in the child actions; never replace a specific request with generic “try a test” language.

Choose the evidence surface deliberately. Use `trial_grid` only for a repeated comparison: run exactly two trials and put only the short name of each version in `evidence_rows`; code supplies TRY 1, TRY 2, and BEST. Use `design_plan` for an invention, build, story, or team plan and provide two to four short labels for the actual drawing and response boxes; never tell the child to fold another page, draw boxes, or make lines the PDF should supply. Use `writing_lines` only for a short open reflection.

For comparisons, say what to build or select, what stays the same, what changes, and what result to mark. Prefer reconfiguring one object between trials when that makes the comparison fairer and faster; require multiple builds only when the learning mechanic truly needs them. Allow multiple valid approaches. Provide a three-step hint ladder from gentle nudge to strong help, but do not reveal the solution immediately. Ask the child to produce evidence—a drawing, test result, arrangement, or explanation—then reflect on what changed. Favor adventure, mystery, construction, comparison, and playful problem solving over quiz language.
